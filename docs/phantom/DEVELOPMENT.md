## 1. 작업 전 확인

이 포크의 규칙이다. 근거는 [FORK-DELTA.md](FORK-DELTA.md) 2절의 히스토리 분석과 README 설계 규칙(`git show be60914099:README.md`의 56-60행, 94-98행)이다.

1. **번들은 설정으로 줄이고 소스는 남긴다.** 플러그인을 뺄 때 모듈 소스, `.idea/modules.xml` 항목, 루트 모듈 의존은 그대로 두고 `build/src/org/jetbrains/intellij/build/IdeaCommunityProperties.kt:90-122`의 번들 목록에서만 뺀다. 업스트림 병합을 쉽게 하려는 것이다(e2a4ffa4ee 본문). IntelliJ 플러그인을 Phantom-plugins 판으로 바꿀 때도 원본은 이 목록에서만 뺀다(9229667cc7, 2절 (c)). 소스를 실제로 지운 경우는 FORK-DELTA 2.1절의 6개 커밋뿐이다.
2. **JetBrains 서버 호출은 지우지 말고 게이트 뒤에 둔다.** 게이트는 `platform/platform-impl/src/com/intellij/ide/plugins/marketplace/MarketplaceRequests.kt:104-109`의 `jetBrainsServicesEnabled`(시스템 프로퍼티 `phantom.jetbrains.services`, 기본 false) 하나다.
3. **패치에 표식 주석을 단다.** 수정한 줄 옆에 `// phantom-idea:`, XML은 `<!-- phantom-idea: -->`. ea745003d1부터 주석을 달 수 있는 수정 업스트림 파일 101개는 모두 수정 덩어리마다 표식이 있다(옛 `// Phantom:` 형식은 ee343c00f6에서 `phantom-idea:`로 통일했다). markdown, JSON, `.iml`, `.idea/modules.xml`, `BUILD.bazel`, API 덤프, 생성 목록, `build.txt`, 이미지 등 주석을 달 수 없는 수정 파일 34개에는 표식이 없다(FORK-DELTA 2절). 표식은 길잡이일 뿐이고, 델타를 찾을 때는 `git diff d2faebf601 HEAD`를 기준으로 삼는다.
4. **새 코드는 `dev.phantom.*` 패키지, 새 모듈은 `phantom.*` 이름**을 쓴다(c06e071a51). 예외는 업스트림 패키지 안의 `platform/lang-impl/src/com/intellij/openapi/projectRoots/impl/jdkDownloader/FoojayJdkList.kt`, `plugins/github/github-core/src/org/jetbrains/plugins/github/authentication/GHDeviceFlow.kt`, `platform/build-scripts/src/org/jetbrains/intellij/build/impl/PhantomBuildNumber.kt`다.
5. **시작 경로를 무겁게 하지 않는다.** README 설계 규칙: 프로젝트가 그 기술을 쓸 때만 동작, 증분 갱신, EDT 작업·불필요한 시작 활동·시작 경로의 네트워크 금지. 현재 코어에는 Phantom `postStartupActivity`가 2개 있다(`platform/platform-resources/src/META-INF/PlatformExtensions.xml:841`, `:843`). 정적 게이트(3절)는 시작 활동 등록 수가 하나라도 늘면 실패한다.
6. **클린룸.** intellij-community API와 공개 스펙만 쓴다. Ultimate 플러그인을 번들하지 않으며, 라이선스 검사를 건드리지 않는다(README 94-98행, 로드맵 `:53`).
7. **업스트림 저장소 규칙은 그대로다.** `*.iml`이 원본이고 정규 형식을 지킨다(주석·재정렬·끝 줄바꿈 추가 금지), 사용자에게 보이는 문자열은 `*.properties`에 둔다([AGENTS.md](../../AGENTS.md)). 기존 Phantom 코드의 하드코딩 문구 39개는 a1313a347c가 리소스 번들로 옮겼다(빌드 전, 5절 4번). 새 Phantom 문구는 `platform/platform-impl/resources/messages/PhantomIdeBundle.properties`(코드는 `dev.phantom.ide.PhantomIdeBundle`, platform-impl)나 `platform/lang-impl/resources/messages/PhantomLangBundle.properties`(`dev.phantom.ide.PhantomLangBundle`, lang-impl)에 키 `phantom.<기능>.<무엇>`으로 넣는다. 번들 이름이 모듈마다 다른 것은 platform-impl과 lang-impl이 코어 클래스 로더를 같이 쓰기 때문이다. 업스트림 번들에 넣어야 하는 것(도구 창 제목은 `IdeBundle`, GitHub 플러그인은 `GithubBundle`)은 파일 끝 `# phantom-idea` 아래에 둔다.
8. **변경마다 [CHANGELOG.md](../../CHANGELOG.md) `미배포` 아래에 항목을 단다**(4절).

## 2. 작업별 방법

현재 번들 목록은 [BUILD.md 1절](BUILD.md#1-한눈에-보기)의 2026-11-18 상태를 본다. 아래 기준 커밋에서 센 17개 대체 플러그인·31개 제거 항목은 당시 값이며, 현재 설정은 각각 26개·40개다. 플러그인 저장소의 해당 모듈은 자체 `src/main` 소스를 빌드한다. 이 포크의 같은 이름 소스를 고쳐도 그 복사본이 자동으로 갱신되지는 않는다.

### IDE에서 소스 열기·실행하기

1. [BUILD.md 2절](BUILD.md#2-사전-준비)의 Android 체크아웃을 준비하고, IDE의 Open으로 **이 저장소 루트**를 연다. 이미 `.idea/modules.xml`과 `*.iml`이 있는 IntelliJ 프로젝트다. `community/` 하위 폴더를 찾거나 Gradle 프로젝트로 새로 가져오지 않는다.
2. Project Structure에서 프로젝트 SDK를 확인한다. 추적된 [`.idea/misc.xml`](../../.idea/misc.xml)의 이름은 `jbr-25`, 언어 수준은 `JDK_25`다. 로컬 SDK 목록에 없다면 JDK 25를 그 이름으로 등록한다. 로컬 경로를 맞추기 위해 추적된 `.iml`이나 `.idea` 파일 전체를 다시 쓰지 않는다.
3. 인덱싱과 의존성 준비가 끝나면 공유 실행 구성 **IDEA**로 실행하거나 디버그한다. [구성 파일](../../.idea/runConfigurations/IDEA.xml)은 `intellij.idea.community.main` 모듈의 `com.intellij.idea.Main`을 실행하며 작업 디렉터리는 `bin/`이다. 개발용 설정은 `config/idea`, 시스템·로그는 `system/idea` 아래를 쓴다. 이 절은 구성 파일을 확인한 안내이며 새 체크아웃에서의 실행 검증은 하지 않았다.
4. 소스 실행의 플러그인 구성과 배포 앱의 번들 구성을 구분한다. 루트 모듈의 런타임 의존은 업스트림 소스를 유지하지만, `phantom-build.sh`는 Phantom-plugins에서 빌드한 대체 플러그인을 번들한다. 대체 플러그인을 고칠 때는 아래 (c)의 소스 출처를 먼저 확인하고, 배포 동작은 `./phantom-build.sh`의 산출물로 검증한다. 소스 실행에서 보이는 버전 0.0은 [BUILD.md 3절](BUILD.md#3-빌드)의 표시 버전 자리표시자다.

### (a) 번들에서 플러그인 빼기

- 언제: 업스트림 플러그인을 Phantom 기본 설치에서 빼고 싶을 때.
- 파일: `build/src/org/jetbrains/intellij/build/IdeaCommunityProperties.kt:90-122`(`.removing(...)` 사슬), 이유 주석 `:82-89`. 빼려는 ID가 업스트림 목록 어디에 있는지는 `platform/build-scripts/src/org/jetbrains/intellij/build/BaseIdeaProperties.kt:14-60`(`IDEA_BUNDLED_PLUGINS`)과 그것이 포함하는 `DEFAULT_BUNDLED_PLUGINS`(`platform/build-scripts/src/org/jetbrains/intellij/build/productLayout/ProductModulesLayout.kt:23-39`)에서 찾는다.
- 순서: (1) `.removing("<모듈>")` 한 줄을 더한다. (2) `:82-89` 주석에 이유를 한 줄 쓴다. (3) 다른 번들 플러그인이 그 모듈에 의존하는지 확인한다(커밋 본문들이 "nothing bundled depends on it"으로 적은 확인). (4) 제품 콘텐츠 모듈이면 `.removing`이 아니라 `intellijCommunityBaseFragment()`(`:262-300`)의 `module(...)` 줄을 지운다(770810693c, `:285` 주석). 소스, `.idea/modules.xml`, `intellij.idea.community.main.iml`은 건드리지 않는다. 예: 7c43a36532는 이 파일 한 개만 바꿨다.
- 검증: 빌드 후 `Phantom.app/Contents/plugins/`에 그 플러그인이 없는지 본다. 정적 게이트(3절)는 감소를 실패로 보지 않는다.

### (b) 뺀 플러그인 되돌리기

- 업스트림 플러그인(소스가 남아 있는 31개, FORK-DELTA 3.2절): `.removing` 줄과 주석을 지운다. 제품 콘텐츠 모듈이면 `module(...)` 줄을 되살린다. 예: a3e497f72d가 `intellij.ide.startup.importSettings`를 `build/src/org/jetbrains/intellij/build/IdeaCommunityProperties.kt:286`로 되살렸다(2줄 변경). Phantom-plugins 판이 대신 들어간 16개(`:106-121`)와 Lombok은 그 판을 `PHANTOM_PLUGINS_BUNDLED`(`:35-38`)와 `phantom-build.sh:33`에서도 빼야 한다. Kotlin(`:122`)을 되돌리면 `pluginModulesToPublish`(`:126`)와 `phantom-release.sh`의 Kotlin zip 확인·게시(`:59-63`, `:81-122`)도 함께 정리해야 한다(추정, 해 본 적 없음). 둘을 같이 넣으면 같은 ID와 모듈을 두 번 차지한다(9229667cc7 본문). 04dba66c3a 뒤로는 그 경우 별칭 대체로 Phantom-plugins 판만 로드될 것으로 보인다(추정, FORK-DELTA 3.12절).
- 소스까지 지운 모듈(FORK-DELTA 2.1절: 프로모 3개, Toolbox, JetBrains OAuth 등): 지운 커밋을 되돌리고 플러그인 기술자(`META-INF/plugin.xml`) 등록과 `.idea/modules.xml` 항목까지 함께 되살려야 한다(추정, 해 본 적 없음).
- Phantom-plugins로 옮긴 플러그인(FORK-DELTA 5.2절 8개, Bytecode Viewer·WebP·Modal Commit 대체판): 이 리포에 되돌리지 않는다. IDE의 Plugins 화면에서 공식 저장소 `newkayak12/Phantom-plugins`로 설치한다.
- 검증: 번들 플러그인 수가 늘면 정적 게이트의 `bundled_plugins`(허용 +0)가 실패한다. 의도한 증가면 같은 커밋에서 `docs/phantom/bench/static-baseline.json`을 새 측정값으로 바꾸고 커밋 본문에 이유를 쓴다. 단 현재 baseline(26.10.27, `bundled_plugins` 56)은 7c43a36532가 `.removing` 5건을 더하기 전 값이라, 되돌리는 플러그인이 5개 이하면 게이트가 실패하지 않는다(추정, 실행하지 않음). 되돌리기 전에 baseline을 새로 측정해 둔다.

### (c) Phantom 모듈·번들 플러그인 추가 (이 리포 vs Phantom-plugins)

- 먼저 어디에 둘지 정한다. 기본은 별도 리포 `newkayak12/Phantom-plugins`다. 거기서 만든 플러그인은 필요할 때 설치하거나, 아래 "Phantom-plugins 판을 번들에 넣기"처럼 이 리포의 빌드가 번들에 넣는다. 이 리포에서 만든 플러그인 10개 중 8개가 결국 그리로 옮겨졌고 `phantom-sync`, `phantom-theme` 2개만 남았다(FORK-DELTA 2절 "트리 안에서 만들고 밖으로 옮긴다", 5.2절). 이 리포에 두는 것은 플랫폼 패치가 필요한 것(GitHub 플러그인 저장소, `PhantomMemorySizer`, Endpoints 창 — 플랫폼 모듈 안에 있음)과 제품 기본값인 것(`phantom-theme`, JetBrains 서비스를 대체하는 `phantom-sync`)뿐이다.
- 이 리포에 번들 플러그인을 더할 때 함께 고치는 파일(5f1819d799가 한 번에 바꾼 목록):

- Bazel 파일 생성기: 이 리포에 있는 것은 `build/jpsModelToBazelCommunityOnly.cmd`뿐이다(업스트림 문서의 `./build/jpsModelToBazel.cmd`는 없다). 확인한 것: 스크립트가 `RUN_WITHOUT_ULTIMATE_ROOT=true`를 켜고(`:8`) `platform/build-scripts/bazel`에서 `bazel.cmd run //:jps-to-bazel`을 실행한다(`:11-12`). 대상은 `platform/build-scripts/bazel/BUILD.bazel:115`이고, 문서상 각 `BUILD.bazel`과 `build/bazel-generated-file-list.txt`를 쓴다(`platform/build-scripts/bazel/README.md:248-252`). 확인하지 못한 것: 이 리포에서 실제로 끝까지 도는지(실행해 보지 않음), Phantom 커밋이 이 명령으로 Bazel 파일을 만들었는지(FORK-DELTA 6.1절). 같은 README `:250`이 만든다는 `build/bazel-targets.json`이 트리에 없어 판단할 수 없다. 돌지 않으면 5f1819d799처럼 같은 형식(`### auto-generated section` 표식, 예 `plugins/phantom-theme/BUILD.bazel:3`)을 손으로 맞춘다.
- 검증: `./tests.cmd --module <새 테스트 모듈> --test 'dev.phantom.<name>.*'`(컴파일 포함), 빌드한 앱의 `Contents/plugins/`에 새 플러그인 존재. 정적 게이트는 `bundled_plugins`와 시작 등록 증가를 실패로 보므로 (b)처럼 기준선을 의도적으로 갱신한다.
- Phantom-plugins 판을 번들에 넣기(IntelliJ 플러그인 대체 포함, 9229667cc7이 한 방법):
  1. Phantom-plugins 쪽: 디렉터리 `<dir>`의 `:<dir>:buildPlugin`이 `<dir>/build/distributions/<dir>-<version>.zip`을 만들고(`<dir>/build.gradle.kts`의 `version = "..."` 줄에서 버전을 읽음), 그 zip이 `<dir>/lib`로 풀려야 한다(`phantom-build.sh:36-43`, `build/src/org/jetbrains/intellij/build/IdeaCommunityProperties.kt:210-211`). IntelliJ 원본을 대체하는 판은 `dev.phantom.*` ID에 원본 ID를 별칭으로, 원본 콘텐츠 모듈 이름을 그대로 둔다(`IdeaCommunityProperties.kt:29-34` 주석. Phantom 자체 구현인 Mermaid `com.phantom.mermaid`만 별칭이 없다). 그래야 원본에 의존하는 번들 플러그인이 대체판으로 해석된다.
  2. 이 리포: `PHANTOM_PLUGINS_BUNDLED`(`IdeaCommunityProperties.kt:35-38`)와 `phantom-build.sh:33`의 `bundled_from_plugins`에 같은 `<dir>`를 더한다(지금 둘 다 17개). 두 목록은 주석으로만 서로를 가리킨다.
  3. 원본이 번들에 있으면 `.removing("<원본 모듈>")`을 `:105` 주석 아래에 더한다(`:106-121`). `PHANTOM_BUNDLED_PLUGINS`에 있던 것이면 그 줄을 지운다(`intellij.lombok` 사례).
  4. 빌드 설정이 원본 플러그인 디렉터리 이름을 쓰는 곳을 찾아 고친다. 예: `CE_CLASS_VERSIONS`의 커버리지 런타임 경로 `plugins/java-coverage/...` → `plugins/coverage/...`(`platform/build-scripts/src/org/jetbrains/intellij/build/BaseIdeaProperties.kt:71`, a199380d7d). `./tools/rg.cmd -n 'plugins/<원본 디렉터리>/' platform/build-scripts build`로 찾는다.

### (h) 새 업스트림 태그로 올리기 (미검증 절차)

이 리포 히스토리에서 한 번도 해 본 적이 없다. 아래는 FORK-DELTA 6절과 저장소 구조에서 세운 절차이고 전부 (추정)이다.

1. 전제: `d2faebf601`은 업스트림 태그 트리를 README 없이 한 번에 넣은 루트 커밋이다(`git rev-list --max-parents=0 HEAD`). 업스트림 히스토리가 없으므로 업스트림 태그를 그대로 `git merge`하면 공통 조상이 없다.

## 3. 검증

[Phantom quality](../../.github/workflows/phantom-quality.yml)는 PR, main push, 수동 실행에서 스크립트·워크플로 검사와 품질 도구의 Node 테스트를 한다. IDE 모듈 테스트, 앱 빌드와 벤치는 아래 명령으로 별도 검증한다. PR 작업 흐름은 [`.ai/workflow.md`](../../.ai/workflow.md), GitHub 규칙 설정은 [`.github/rulesets/README.md`](../../.github/rulesets/README.md)를 본다.

로컬에서는 `node --test tools/phantom-quality.test.mjs`와 `node tools/phantom-quality.mjs --base origin/main`을 실행한다(Node 22 이상, Python 3, Bash/Zsh 필요). 기본 base는 업스트림 스냅샷 `d2faebf601`이며, 지정한 base와 HEAD의 공통 조상부터 작업 트리까지 변경된 파일과 ignore되지 않은 새 파일을 검사한다. `--lint`를 `--base` 앞에 붙이면 ShellCheck와 actionlint도 실행한다. 두 도구는 PATH에 있어야 하고, CI는 ShellCheck와 Zsh를 Ubuntu 패키지로, actionlint `v1.7.7`을 Go로 설치한다. ShellCheck는 Bash 스크립트의 error 수준, actionlint는 변경된 워크플로를 검사한다.

참고한 [prototype-reservation-system](https://github.com/newkayak12/prototype-reservation-system)의 Detekt 설정을 이 모노레포 전체에 적용하지는 않는다. Kotlin/Java는 영향 모듈의 IDE 검사·컴파일·테스트로 검증한다. 별도 Phantom analysis CI는 Node 품질 도구의 LCOV를 생성하고, 설정이 갖춰지면 Codecov에 올리고 Phantom 소유 소스를 SonarQube로 분석한다. 서비스 설정과 라벨·이슈 자동화는 [GitHub 자동화 안내](../../.github/README.md)를 본다. JVM 커버리지는 포함하지 않는다.

## 4. 커밋·변경 이력 규칙

- 제목: 평범한 영어 명령문 한 줄. 무엇이 달라지는지를 쓴다. 예: `Download JDK lists JDKs from foojay, not JetBrains' feed`(be60914099), `Drop Toolbox App integration`(43b28af952).
- 접두어: 한 플러그인·도구에 한정되면 `phantom-spring:`, `phantom-install:`, `Phantom bench:`, `HTTP client:`, `Workspaces:`처럼 대상 이름을 붙인다(히스토리에서 읽은 관례). 플랫폼 전반 변경은 접두어 없이 쓴다.
- 본문: 메커니즘(무엇을 어디서 막거나 바꿨는지), 이유, 되살리는 플래그(`-Dphantom.jetbrains.services=true` 등), 측정값이 있으면 숫자. be60914099 본문이 전형이다.
- 업스트림 커밋 규칙은 쓰지 않는다: `.agents/skills/commits/SKILL.md`는 JetBrains 형식(YouTrack 티켓, SafePush 검증)을 요구하지만 이 포크 히스토리는 그 형식을 쓰지 않는다.
- CHANGELOG: `CHANGELOG.md:7-14`의 규칙대로 같은 커밋에서 `미배포` 아래 고정 카테고리에 한 줄을 더하고, 끝의 괄호에 넣는 커밋 해시와 PR 번호(`(해시, PR #N)`, PR 없이 main에 넣은 커밋은 해시만)는 다음 커밋에서 채운다. 릴리스 태그가 생기면 `미배포` 항목을 그 버전 아래로 옮긴다.
- 문서: 패치 지점이 바뀌면 FORK-DELTA의 해당 표를, 빌드 스크립트가 바뀌면 BUILD.md를 고친다. 유지 규칙은 [README.md](README.md) "문서 유지 규칙".
