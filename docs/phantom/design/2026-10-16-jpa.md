# phantom-jpa 설계: JPA / Hibernate / Spring Data JPA 지원

- 날짜: 2026-10-16
- 대상 트리: `phantom-idea` (intellij-community `idea/262.10968.63`, 커밋 `ff3de2d3b8`)
- 상태: 설계 초안. 이 문서 외에 소스는 바꾸지 않았다.
- 표기: **[V]** = 이 트리나 사용자 프로젝트에서 경로·API·사실을 직접 확인함. **[A]** = 확인하지 않은 가정 (공개 문서 지식이나 플랫폼 동작에 대한 추정).
- 클린룸: 설계 근거는 (1) `Intellij-rea/reversed/`의 동작·비용 설명 노트, (2) Ultimate 설치본의 plugin.xml에 적힌 기능 이름, (3) 커뮤니티 API, (4) Jakarta Persistence / Spring Data 공개 명세다. `reversed/source/`는 열지 않았고 디컴파일 코드는 참고하지 않았다.

### 1.2 MVP (v0.1)

매일 쓰는 것만 넣는다.

1. **엔티티 모델**: `@Entity`, `@MappedSuperclass`, `@Embeddable`, `@Id`/`@EmbeddedId`/`@Version`, `@Column`, `@Transient`, `@Embedded`, `@ElementCollection`, `@ManyToOne`/`@OneToOne`/`@OneToMany`/`@ManyToMany`(+`mappedBy`, `targetEntity`), `@Table`(이름만 기록), `@Access`. `jakarta.persistence`와 `javax.persistence` 둘 다. Java와 Kotlin 소스 모두.
2. **JPQL 언어**: Jakarta Persistence 3.1 JPQL 문법의 렉서·파서·하이라이터·괄호 매칭. Hibernate HQL 확장 중 자주 쓰는 일부(`LIMIT/OFFSET`)는 관대하게 받아들인다.
3. **JPQL 주입(injection)**: 아래 위치의 문자열에 JPQL을 주입한다.
   - `@org.springframework.data.jpa.repository.Query`의 `value`, `countQuery` (단 `nativeQuery = true`이면 주입하지 않음)
   - `@jakarta.persistence.NamedQuery` / `@javax.persistence.NamedQuery`의 `query`
   - **같은 파일 안의 `const val`(Kotlin)·`static final String`(Java) 초기값 중 위 어노테이션에서 쓰이는 것**. 사용자 쿼리의 80%가 이 형식이라 MVP에서 빠질 수 없다
   - Kotlin 문자열 템플릿 `$CONST`는 자리표시자로 처리한다 (§3.6)
   - `// language=JPQL` 주석 (IntelliLang 주석 주입이 언어 ID로 자동 처리, [A])
4. **JPQL 코드 인사이트**: 엔티티 이름, 식별 변수(alias), 속성 경로(`r.timeTable.timeTableId`, 임베디드·연관 따라가기), `:name` 파라미터의 참조(Ctrl+클릭, 이름 변경 반영)와 자동 완성. 키워드 완성.
5. **Spring Data 파생 쿼리**: 리포지토리 인터페이스의 메서드 이름(`findBy...And...OrderBy...Desc`) 파싱, 속성 경로 해석, 잘못된 속성 하이라이트, 메서드 이름 자동 완성, 이동(Ctrl+클릭).
6. **기본 inspection** (6개, §3.8): 엔티티에 ID 없음, JPQL 미해결 엔티티/속성, JPQL 파라미터와 메서드 파라미터 불일치, `mappedBy` 미해결, 파생 쿼리 속성 미해결/인자 개수 불일치, `UPDATE`/`DELETE` `@Query`에 `@Modifying` 없음.
7. **Implicit usage**: JPA가 리플렉션으로 쓰는 엔티티 필드, 기본 생성자, `@PrePersist` 등 콜백 메서드를 "사용되지 않음" 경고에서 뺀다.

### 1.4 비목표 (하지 않는다)

- **Database Tools 연동 일체**: 데이터 소스, DB 연결, 스키마 검증(컬럼/테이블 존재 확인), SQL 콘솔, JPA 콘솔, DB→엔티티 생성(reverse engineering), DDL 생성. Ultimate는 JPA/Hibernate가 DB 플러그인(클래스 3.8k, Metaspace 19 MB)에 하드 의존한다. phantom-jpa는 DB 플러그인 없이 동작해야 한다.
- `nativeQuery = true`의 SQL 주입. 커뮤니티에는 SQL 언어가 없다 [V: 트리에 SQL 플러그인 없음]. 필요하면 별도 플러그인이 같은 위치에 SQL을 주입하도록 확장점만 남긴다.
- `persistence.xml`, `orm.xml`, `hbm.xml` 등 XML 매핑과 DOM 모델. Spring Boot 프로젝트는 쓰지 않는다.
- JPA 구조 툴 창, ER 다이어그램, DTO/프로젝션 생성 마법사, Liquibase/Flyway 연동 (JPA Model·JPA Buddy가 하는 일).
- Criteria API·정적 메타모델(`Entity_`) 해석, Jakarta Data, Spring Data JDBC/MongoDB/Redis 리포지토리.
- 라이선스·인증 관련 코드.

| JPA Model + JPA Buddy가 같은 일을 두 벌로 함 (observed) | JPA 모델은 phantom-jpa 하나. phantom-spring 등 다른 플러그인은 `JpaFacade` API로만 접근 |

추가 규칙:

1. **활성화**: 모듈의 라이브러리에 `jakarta.persistence.Entity` 또는 `javax.persistence.Entity`가 있을 때만 켠다. Spring Data 기능은 `org.springframework.data.repository.Repository`가 있을 때만. `JavaLibraryUtil.hasLibraryClass(module, fqn)`이 `JavaLibraryModificationTracker`로 캐시한다 [V: `java/openapi/src/com/intellij/java/library/JavaLibraryUtil.java:119`, `JavaLibraryModificationTracker.java`].
2. **증분 모델**: 캐시 의존성은 해당 클래스의 `PsiFile`이다. 한 파일을 고치면 그 파일의 요약만 무효화된다. 프로젝트 전역 `PsiModificationTracker.MODIFICATION_COUNT`는 쓰지 않는다. 전역 집계가 꼭 필요한 곳(완성용 엔티티 이름 목록)만 `UastModificationTracker`(Java/Kotlin 언어별 트래커의 합)에 걸고, 완성 때만 계산한다 [V: `java/java-analysis-api/src/com/intellij/uast/UastModificationTracker.kt`. `PsiModificationTracker` 주석이 "모든 PSI 변경"이라 비싸다고 경고한다].
3. **지연 서비스**: 서비스는 `@Service(Service.Level.PROJECT)` light service만 쓰고 처음 쓸 때 생성된다. application service는 없다.
4. **EDT 작업 없음**: 모든 계산은 데몬·완성·inspection이 이미 돌고 있는 백그라운드 읽기 액션 안에서 한다. UI 액션은 v0.1에 없다.
5. **Dumb mode**: 렉서·파서·하이라이터는 `DumbAware`로 인덱싱 중에도 동작한다. 해석(reference resolve), 완성, inspection은 dumb 모드에서 자동으로 빠지게 둔다(DumbAware 미구현).

## 3. 아키텍처

### 3.1 모듈 배치

TOML 플러그인의 콘텐츠 모듈 구성(`plugins/toml/resources/META-INF/plugin.xml`의 `<content>`, `plugins/toml/plugin-content.yaml`, `core/src/gen` + `core/src/main/grammars`)을 본뜬다 [V].

```
plugins/phantom-jpa/
├── resources/META-INF/plugin.xml          # id = "phantom.jpa", <content> 선언, depends: com.intellij.java
├── plugin-content.yaml
├── BUILD.bazel, phantom.jpa.iml
├── core/        → phantom.jpa.core      (loading="embedded")
│   ├── src/main/grammars/Jpql.bnf, _JpqlLexer.flex
│   ├── src/gen/...                               # Grammar-Kit/JFlex 생성물 (커밋)
│   └── src/main/kotlin/.../{lang,model,api}      # JpqlLanguage, PSI, JpaFacade, 모델 타입
├── backend/     → phantom.jpa.backend
│   └── injection, references, completion, inspections, implicit usage
├── kotlin/      → phantom.jpa.kotlin    # <plugin id="org.jetbrains.kotlin"/>
│   └── KtStringTemplateExpression 주입, Kotlin const val 추적, (v0.2) Kotlin inspection
├── spring-data/ → phantom.jpa.springData
│   └── 파생 쿼리 파서, 리포지토리 모델, @Query 파라미터 검사, @Modifying 검사
└── tests/       → phantom.jpa.tests
```

- 콘텐츠 모듈 디스크립터의 `<dependencies><module name=.../><plugin id=.../></dependencies>` 형식 [V: `plugins/toml/json/src/main/resources/intellij.toml.json.xml`, `plugins/env-files-support/kotlin/resources/intellij.dotenv.kotlin.xml`의 `<plugin id="org.jetbrains.kotlin"/>`].
- 번들 등록: `platform/build-scripts/src/org/jetbrains/intellij/build/BaseIdeaProperties.kt`의 `IDEA_BUNDLED_PLUGINS`에 `"phantom.jpa"`를 추가 [V: 목록 존재, `"intellij.toml"`이 같은 방식으로 들어 있음]. Bazel 타깃 생성 절차(JPS `.iml` → `BUILD.bazel`)는 [A], 첫 작업에서 확인.
- phantom-spring 설계와의 경계: Spring Data 파생 쿼리는 엔티티 모델에 강하게 묶이므로 여기에 둔다. phantom-spring은 `phantom.jpa`의 `JpaFacade`를 선택 의존으로 쓴다 [A: 다른 설계 문서와 맞춰야 함].

| UAST 상수 평가 | `UExpression.evaluateString()` | `uast/uast-common/src/org/jetbrains/uast/UastUtils.kt:163` |
| UAST 참조 등록 | `registerUastReferenceProvider`, `uastInjectionHostReferenceProvider` | `uast/uast-common-ide/src/com/intellij/psi/UastReferenceRegistrar.kt` |
| Kotlin K2 UAST | `uast-kotlin-fir`, `uast-kotlin-idea-fir` | `plugins/kotlin/uast/` |

**주입 방식 결정**: IntelliLang `injectionConfig` XML(`java/langInjection/resources/resources/javaInjections.xml` 형식)로 `psiMethod().withName("value").definedInClass("...Query")`를 선언하면 Java와 Kotlin 어노테이션 인자 둘 다 주입된다 [V: `KotlinLanguageInjectionContributorBase.injectInAnnotationCall`이 어노테이션 클래스의 메서드를 찾아 Java 주입 설정을 조회]. 그러나 (a) `nativeQuery = true` 같은 형제 인자 조건, (b) 사용자 쿼리의 대부분인 `const val` 간접 참조를 표현할 수 없다. 그래서 **자체 `MultiHostInjector`** 를 쓴다. IntelliLang에는 의존하지 않는다(주석 주입은 IntelliLang이 설치돼 있으면 덤으로 동작).

### 3.3 데이터 모델

```kotlin
// core/api — 다른 플러그인에 공개하는 유일한 진입점
@Service(Service.Level.PROJECT)
class JpaFacade(project: Project) {
  fun isEnabled(module: Module): Boolean                         // JavaLibraryUtil 기반
  fun getEntityModel(cls: PsiClass): JpaClassSummary?            // 파일 단위 캐시
  fun findEntityByName(name: String, context: PsiElement): PsiClass?
  fun allEntityNames(module: Module): Collection<String>         // 완성 전용
  fun resolvePath(root: PsiClass, path: List<String>): JpaAttribute?
}

enum class JpaClassKind { ENTITY, MAPPED_SUPERCLASS, EMBEDDABLE }
enum class AccessType { FIELD, PROPERTY }

class JpaClassSummary(                 // 클래스가 "직접" 선언한 것만 담는다
  val kind: JpaClassKind,
  val entityName: String?,             // @Entity(name) ?: simple name
  val tableName: String?,              // 표시용. 스키마 검증에는 안 씀
  val accessType: AccessType,          // @Access ?: @Id/@EmbeddedId 위치
  val declaredAttributes: List<JpaAttribute>,
)

enum class AttrKind { BASIC, ID, EMBEDDED_ID, VERSION, EMBEDDED, ELEMENT_COLLECTION,
                      MANY_TO_ONE, ONE_TO_ONE, ONE_TO_MANY, MANY_TO_MANY }

class JpaAttribute(
  val name: String,                    // JPQL에서 쓰는 이름 (필드 이름 또는 getter 프로퍼티 이름)
  val kind: AttrKind,
  val element: PsiMember,              // PsiField / getter. Kotlin은 light 요소, navigationElement로 KtProperty
  val valueType: PsiType,              // 컬렉션이면 요소 타입(제네릭 인자 or targetEntity)
  val mappedBy: String?,
)
```

- 상속 체인(`@MappedSuperclass` → `@Entity`)은 요약에 합치지 않는다. `resolvePath`·`allAttributes(cls)`가 조회 시 상위 클래스 요약을 각자의 캐시에서 꺼내 합친다. 그래서 상위 클래스 파일을 고쳐도 하위 클래스 요약이 무효화되지 않는다.
- **모델 소스**: 타입 정보는 Java PSI 관점(`PsiClass.getFields()`, Kotlin은 light class)으로 얻는다. 어노테이션 인자 값(`mappedBy`, `name`, `targetEntity`)은 `PsiAnnotation.findAttributeValue` 후 상수 평가. Kotlin `@Id private var id`의 `@Id`는 Java 어노테이션이라 Kotlin `PROPERTY` 대상이 될 수 없어 백킹 필드에 붙는다 → light field 어노테이션으로 보인다 [A: Kotlin 어노테이션 use-site 규칙, 테스트로 확인]. 생성자 파라미터 프로퍼티(`class E(@Id val id: Long)`)는 파라미터에 붙어 필드에서 안 보인다. 이 경우는 v0.2 inspection 대상이다.
- **엔티티 이름 해석** (`FROM ReservationEntity`): 1단계로 `PsiShortNamesCache.getClassesByName(name, moduleScope)`에서 `@Entity` 클래스를 찾는다 (흔한 경우, 인덱스 조회 1회). 실패하면 2단계로 `allEntityNames(module)` 맵에서 `@Entity(name="...")` 커스텀 이름을 찾는다.
- **범위**: 모든 검색은 `GlobalSearchScope.moduleWithDependenciesAndLibrariesScope(module)`. 사용자 작업 공간에 같은 FQN 엔티티가 4벌 있으므로 프로젝트 전체 범위를 쓰면 엉뚱한 사본으로 이동한다 [V: §1.1].

Spring Data 모델 (spring-data 모듈):

```kotlin
class RepositoryInfo(val iface: PsiClass, val domainClass: PsiClass, val idType: PsiType)
// domainClass = getSuperClassSubstitutor(Repository, iface).substitute(T)

class DerivedQuery(                  // 순수 Kotlin. PSI 없음. 단위 테스트 쉬움
  val subject: Subject,              // FIND/READ/GET/QUERY/SEARCH/STREAM/COUNT/EXISTS/DELETE/REMOVE
```

연산자 집합은 Spring Data JPA 참조 문서의 키워드 표를 따른다 [A: 공개 문서 지식]: `Is/Equals`, `Not`, `Between`, `LessThan(Equal)`, `GreaterThan(Equal)`, `After`, `Before`, `IsNull/Null`, `IsNotNull/NotNull`, `Like`, `NotLike`, `StartingWith`, `EndingWith`, `Containing`, `In`, `NotIn`, `True`, `False`, `IgnoreCase`, `AllIgnoreCase`, `OrderBy...Asc/Desc`. 속성 경로는 Spring Data 규칙대로 전체 이름 → 오른쪽 camel-case 혹 단위로 분할하며 탐색하고, `_`는 명시적 경계로 본다.

### 3.4 캐시와 무효화

| 캐시 | 키(저장 위치) | 의존성 | 계산 시점 |
|---|---|---|---|
| `JpaClassSummary` | `PsiClass` 사용자 데이터 | 그 클래스의 `PsiFile` | 첫 조회 |
| 파일 내 "`@Query`/`@NamedQuery`에서 쓰이는 상수 이름 집합" | `PsiFile` | 그 `PsiFile` | 주입기가 상수 초기값을 만났을 때 |
| `RepositoryInfo` | `PsiClass`(인터페이스) | 그 파일 + `JavaLibraryModificationTracker` | 첫 조회 |
| `DerivedQuery` | `PsiMethod` | 그 파일 | 첫 조회 |
| `allEntityNames(module)` | `Module` | `UastModificationTracker` | 완성, 2단계 이름 해석 때만 |
| 활성화 여부 | `JavaLibraryUtil` 내부 | 라이브러리 트래커 | 첫 확장 호출 |
| JPQL 주입 결과 | 플랫폼(`InjectedLanguageManager`)이 호스트 단위로 관리 [A] | 호스트 문자열 | 데몬 |

교차 파일 참조(JPQL 속성 → 다른 파일의 엔티티)는 캐시하지 않는다. `PsiReference.resolve()`는 플랫폼의 `ResolveCache`에 맡긴다 [A]. 이렇게 하면 엔티티 파일을 고쳐도 쿼리 파일 쪽은 다음 하이라이트 때 다시 해석될 뿐이고, 전역 무효화가 없다.

### 3.5 JPQL 문법

- 근거: Jakarta Persistence 3.1 명세 4.14절 BNF [A: 공개 명세 지식]. 지원 범위: `select_statement`/`update_statement`/`delete_statement`, `FROM` 범위 변수, `[LEFT [OUTER] | INNER] JOIN [FETCH] path [AS] alias [ON cond]`, 컬렉션 멤버 선언 `IN(...)`, 경로식, 조건식(`AND/OR/NOT`, 비교, `BETWEEN`, `IN`, `LIKE ... ESCAPE`, `IS [NOT] NULL`, `IS [NOT] EMPTY`, `[NOT] MEMBER [OF]`, `EXISTS`, `ALL/ANY/SOME` 서브쿼리), `GROUP BY`, `HAVING`, `ORDER BY ... ASC|DESC`, `SELECT [DISTINCT]`, `NEW` 생성자 표현식, 집계 함수, `CASE`, `COALESCE`, `NULLIF`, 문자열·수치·시간 함수, `FUNCTION('name', ...)`, `KEY/VALUE/ENTRY`, `TYPE`, `TREAT`, 파라미터 `:name`/`?1`, 리터럴(문자열, 숫자, 불리언, `{d '...'}` 등), enum 리터럴 FQN.
- 관대함: 모르는 함수 이름은 일반 함수 호출로 파싱한다(HQL 함수 대응). `LIMIT n`, `OFFSET n`, `FETCH FIRST n ROWS ONLY`는 HQL 확장으로 받는다. 키워드는 대소문자 무시.
- 오류 복구: Grammar-Kit `pin`/`recoverWhile`로 절(clause) 단위 복구. 입력 중인 쿼리에서 이후 절 하이라이트가 깨지지 않게 한다.
- PSI 크기: 노드 타입을 줄인다. 이항식은 `JpqlBinaryExpression` 하나(연산자 토큰으로 구분), 함수는 `JpqlFunctionCall` 하나. 참조가 필요한 노드만 별도 타입: `JpqlEntityName`, `JpqlAliasDeclaration`, `JpqlPathExpression`(세그먼트마다 reference), `JpqlParameter`.
- 생성: Grammar-Kit과 JFlex는 트리의 빌드 단계에 없다 [V: `*.bazel`, `*.bzl`, `*.iml`에서 grammar-kit 문자열 없음]. TOML·JSON처럼 생성물을 `src/gen`에 커밋한다 [V: `plugins/toml/core/src/gen/.../TomlParser.java` 첫 줄 "This is a generated file"]. 생성기는 개발 머신의 Grammar-Kit 플러그인 또는 CLI로 실행 [A].

### 3.6 주입기 동작 (`JpqlQueryInjector : MultiHostInjector`)

`elementsToInjectIn()` = Java `PsiLiteralExpression`(backend 모듈), Kotlin `KtStringTemplateExpression`(kotlin 모듈, 같은 로직을 공유하는 별도 등록). 호스트마다 아래 순서로 빨리 거른다. 앞 단계에서 대부분 탈락한다.

1. 호스트가 문자열이 아니거나 길이 < 6 → 종료.
2. `JpaActivation.isEnabled(module)` 아니면 종료 (캐시 조회).
3. **직접 인자인 경우**: 부모 체인에서 어노테이션을 찾고 짧은 이름이 `Query`/`NamedQuery`가 아니면 종료(텍스트 비교, resolve 없음). 그다음 FQN 확인(UAST `UAnnotation.qualifiedName` 또는 import 비교). 인자 이름이 `value`/`countQuery`/`query`인지, 형제 인자 `nativeQuery`가 `true`가 아닌지 본다.
4. **상수 초기값인 경우**: 호스트가 Kotlin `const val` 또는 Java `static final String` 필드의 초기값이면, 파일 캐시 "`@Query`에서 쓰이는 상수 이름 집합"에 그 이름이 있는지 본다. 집합은 파일 안 `@Query`/`@NamedQuery` 인자 중 단순 이름 참조를 모아 만든다(파일당 1회). 같은 파일 안 다른 const의 템플릿 안에서만 쓰이는 상수(예: `SLOT_CONDITION`)도 "조각(fragment)"으로 표시한다.
5. 주입: Kotlin 템플릿 `$NAME`/`${...}` 엔트리는 주입 범위에서 빼고, 그 자리에 prefix 텍스트 `__PH__`를 넣는다. 렉서는 `__PH__`를 `PLACEHOLDER` 토큰으로, 파서는 조건식·스칼라식 위치의 기본식(primary)으로 받는다. 조각 상수는 시작 규칙을 `conditional_expression`으로 하는 별도 파일 요소 타입(`JpqlFragmentFile` 모드)으로 파싱한다. 구현은 `MultiHostRegistrar.startInjecting(lang).addPlace(prefix, suffix, host, range)...doneInjecting()` [V: API 존재. 조각 모드 전환은 prefix에 표식 토큰을 넣어 파서가 분기하는 방식, A].
6. 자리표시자가 있는 쿼리에서는 "미해결 속성/별칭" inspection이 자리표시자에 들어 있을 수 있는 alias를 모르는 상태이므로, 미해결 alias 경고를 내지 않는다(v0.2에서 상수 값을 펼쳐 정확히 처리).

### 3.7 참조와 완성

- `JpqlEntityName` → `PsiClass` (§3.3 이름 해석). 이름 변경 시 `@Entity(name)`이 없으면 클래스 이름 변경을 쿼리 문자열에 반영(`handleElementRename`).
- `JpqlPathExpression` 첫 세그먼트 → `JpqlAliasDeclaration`. 다음 세그먼트 → `JpaAttribute.element`. 임베디드는 `@Embeddable` 클래스 요약으로, 연관은 대상 엔티티로, 컬렉션 연관은 요소 타입으로 이어서 해석한다. 컬렉션 값 경로를 `.`으로 더 따라가면 JPQL 규칙상 오류다(JOIN 필요). v0.1에서는 경고 수준.
- `JpqlParameter`(`:timeTableId`) → 주입 원래 위치가 `@Query`이면 해당 메서드의 파라미터. 파라미터 이름은 `@Param("x")`가 있으면 그것, 없으면 소스 파라미터 이름. Spring Data는 `-parameters` 컴파일 옵션 또는 Kotlin 메타데이터로 이름을 얻는다 [A]. 사용자 프로젝트(`infro/`)에서 `@Param`·`@Modifying`·`@EntityGraph`를 다 합쳐 1회 나오므로 거의 전부 이름 기반이다 [V].
- 완성 (`JpqlCompletionContributor`, language="JPQL"): `FROM`/`JOIN` 뒤 엔티티 이름, 경로 `.` 뒤 속성(종류 아이콘: id, 연관, 임베디드), `:` 뒤 메서드 파라미터 이름, 절 위치별 키워드. 별칭은 같은 쿼리의 선언에서.
- Spring Data 메서드 이름: Java/Kotlin 메서드 선언 이름 위치에서 `findBy`, `existsBy`, `countBy`, `deleteBy` 접두사 + 도메인 속성 + 연산자 키워드 완성. 이동은 `GotoDeclarationHandler`가 메서드 이름 식별자 안의 `Part.pathRange`를 보고 속성으로 보낸다. 잘못된 속성은 `Annotator`가 해당 범위만 빨간 밑줄.

### 3.9 Kotlin K2

- UAST는 K2 구현(`plugins/kotlin/uast/uast-kotlin-fir`, `uast-kotlin-idea-fir`)이 있다 [V]. phantom-jpa는 Analysis API(`analyze {}`)를 직접 부르지 않고 UAST와 light class만 쓴다. 이유: (1) K1/K2 양쪽에서 같은 코드가 돈다, (2) Analysis API 세션 비용을 클래스당 1회 요약으로 묶을 수 있다.
- Kotlin 전용 코드는 `phantom.jpa.kotlin` 모듈에만 둔다: `KtStringTemplateExpression` 주입(템플릿 엔트리 자리표시자), `KtProperty`의 `const` 판정, 같은 파일 상수 참조 수집(PSI만, resolve 없이 이름 비교 후 필요할 때만 `ReferencesSearch`+`LocalSearchScope`).
- Kotlin JPA 컴파일러 플러그인 인식(v0.2 inspection)은 커뮤니티 Gradle 구성기의 `"jpa"` 컴파일러 플러그인 ID 처리를 재사용할 수 있는지 본다 [V: `plugins/kotlin/gradle/gradle-java/src/org/jetbrains/kotlin/idea/gradleJava/configuration/gradleKotlinCompilerPluginProjectConfigurators.kt:220`, `plugins/kotlin/compiler-plugins/noarg/maven/.../NoArgMavenProjectImportHandler.kt:27`].

## 5. 테스트 방법

### 5.1 자동 테스트 (커뮤니티 테스트 프레임워크)

- Java 쪽: `LightJavaCodeInsightFixtureTestCase` [V: `java/testFramework/src/com/intellij/testFramework/fixtures/LightJavaCodeInsightFixtureTestCase.java`]. JPA·Spring Data 어노테이션은 네트워크 없이 `myFixture.addClass("package jakarta.persistence; public @interface Entity { String name() default \"\"; }")`처럼 스텁 소스로 넣는다 [V: `JavaCodeInsightTestFixture.addClass`]. 실제 jar가 필요하면 `DefaultLightProjectDescriptor.withRepositoryLibrary("jakarta.persistence:jakarta.persistence-api:3.1.0")` [V: 메서드 존재, 오프라인 저장소 동작은 A].
- Kotlin 쪽: `KotlinLightCodeInsightFixtureTestCase` [V: `plugins/kotlin/test-framework/test/org/jetbrains/kotlin/idea/test/KotlinLightCodeInsightFixtureTestCase.kt`]를 K2 모드로 실행 (K2 모드 지정 방식은 `plugins/kotlin/base/plugin/src/.../KotlinPluginModeProvider.kt` 주변 확인 필요 [A]).
- 테스트 종류:
  - 파서: `ParsingTestCase` 스타일로 `testData/parser/*.jpql` → PSI 트리 덤프 골든 파일. 사용자 쿼리 36개를 익명화한 형태 포함.
  - 파생 쿼리 파서: PSI 없는 순수 단위 테스트 (메서드 이름 → `DerivedQuery`).
  - 주입: `myFixture.configureByText("Repo.kt", ...)` 후 `InjectedLanguageManager`로 캐럿 위치 언어가 JPQL인지, `nativeQuery = true`일 때 아닌지, const 간접 참조·템플릿 자리표시자.
  - 완성: `myFixture.completeBasic()` + `lookupElementStrings`.
  - 참조/이름 변경: `myFixture.renameElementAtCaret` 후 쿼리 텍스트 비교.
  - inspection: `myFixture.enableInspections(...)` + `checkHighlighting()` (`<error>` 마크업).
  - 비활성화: JPA 라이브러리 없는 프로젝트에서 같은 파일에 주입·하이라이트가 전혀 없는지.

### 5.2 사용자 프로젝트 수동 확인 (`~/orca/workspaces/prototype-reservation-system`)

1. `infro` 프로젝트를 열고 인덱싱이 끝난 뒤 `ReservationJpaRepository.kt`, `WaitingQueueJpaRepository.kt`, `TimeTableOccupancyJpaRepository.kt`를 연다. 쿼리 상수에 JPQL 하이라이트가 있고 오류가 0개여야 한다.
2. 쿼리 안 엔티티·속성 Ctrl+클릭이 **같은 빌드(`infro/`)** 의 클래스로 가야 한다. `feat-contract/` 등 사본으로 가면 범위 버그다.
3. 엔티티 하나에서 속성 이름을 바꿨다가 되돌리며 쿼리·파생 메서드에 오류가 생기고 사라지는지 본다.
4. `Analyze → Inspect Code`를 `infrastructure-module`에 대해 phantom-jpa inspection만 켜고 실행. 오탐 0이 목표. 오탐은 테스트 데이터로 옮긴다.

### 5.3 비용 확인 (Ultimate 측정과 같은 방법)

`Intellij-rea/reversed/02-runtime/`에서 쓴 절차를 Phantom IDEA에 그대로 적용한다.

- `jcmd <pid> GC.class_histogram | grep phantom.jpa` → 적재 클래스 수 (목표 ≤150).
- `jcmd <pid> VM.metaspace` 또는 `VM.classloader_stats` → phantom-jpa 로더 Metaspace.
- 시작 JFR(`-XX:StartFlightRecording`)에서 `phantom.jpa` 프레임이 프로젝트 열기 후 첫 편집 전까지 0이어야 한다 (startup activity·리스너가 없으므로).
- 큰 쿼리 파일에서 타이핑 중 JFR: `JpqlQueryInjector.getLanguagesToInject` 누적 시간이 데몬 전체의 1% 미만 [A: 목표치].
