# phantom-containers 설계: Docker와 Kubernetes

- 작성일: 2026-10-16
- 대상 트리: `phantom-idea` (intellij-community `idea/262.10968.63` 포크, `main`)
- 대상 사용자: Kotlin + Spring Boot + JPA + Gradle 백엔드 개발자
- 표기 규칙
  - **[V]** verified: 이 문서를 쓰면서 경로, 클래스, 확장점, 파일이 실제로 있는지 직접 확인했다.
  - **[A]** assumed: 공개 문서나 일반 지식에 기댄 가정이다. 구현 전에 확인해야 한다.
  - **[M]** measured: `Intellij-rea/reversed/` 분석 노트에 기록된 Ultimate 측정값이다.
  - **[U]** unknown: 아직 측정이나 확인 방법이 없는 의문이다.
- 클린룸 규칙
  - Ultimate 쪽 입력은 두 가지만 썼다. 하나는 `reversed/` 노트의 동작과 비용 설명, 다른 하나는 설치본 `plugin.xml`에 적힌 기능 이름이다(인스펙션 shortName, fileType 이름, 확장점 종류).
  - `reversed/source/`와 디컴파일 코드는 열지 않았다.
  - 라이선스와 인증 코드는 다루지 않는다.

## 1. 목표와 범위

### 1.1 사용자 프로젝트에서 확인한 사실

`~/orca/workspaces/prototype-reservation-system`을 확인한 결과는 다음과 같다.

- 워크트리(`infro`, `feat-command-core`, `feat-contract`, `docs-readme`)마다 `compose.yaml`과 `compose-advanced.yaml`이 있다 [V].
  - 파일 이름이 `docker-compose.yml`이 아니다. 그래서 파일 이름 매칭은 `compose*.yaml`까지 받아야 한다.
- `infro/compose.yaml`의 서비스는 `mysql`, `redis`, `kafka-1`, `kafka-2`, `kafka-3`, `kafka-ui`이고, named volume이 4개다 [V].
- Dockerfile은 깊이 4까지 찾았지만 없다 [V]. Kubernetes 매니페스트(`kustomization.yaml`, `Chart.yaml`, `k8s/`)도 없다 [V].
- `build.gradle.kts`가 `testcontainers-bom`을 쓴다 [V]. `HELP.md`에는 Spring Boot Docker Compose Support 링크가 있다 [V].
  - 따라서 테스트를 돌리면 Testcontainers 컨테이너(`org.testcontainers` 라벨)가 생긴다 [A].
- 로컬 Docker 소켓은 `~/.docker/run/docker.sock`(Docker Desktop)이다. `/var/run/docker.sock`은 이 소켓을 가리키는 심볼릭 링크다 [V].
- `docker`와 `kubectl`은 `/usr/local/bin`에 있다. `~/.kube/config`도 있다 [V].

결론적으로 매일 쓰는 기능은 **Compose 파일 편집, 인프라 컨테이너 up/down, 로그 보기, 컨테이너 셸**이다. Kubernetes는 설치만 돼 있고 이 프로젝트에서는 쓰지 않는다. 그래서 MVP는 Docker와 Compose에 집중한다.

### 1.2 MVP (v0.1)

| # | 기능 | 사용자가 보는 것 |
|---|------|------------------|
| D1 | Dockerfile 구문 강조 | `Dockerfile`, `*.dockerfile`, `Containerfile`을 열면 키워드에 색이 입혀진다. community TextMate의 docker 번들을 그대로 쓴다 |
| D2 | Compose 스키마 검증과 완성 | `compose.yaml`, `compose-*.yaml`, `docker-compose*.yml`에서 키 완성, 알 수 없는 키 오류, `restart:` 같은 열거값 완성이 된다 |
| D3 | Compose 거터 실행 | `services:` 줄 거터에서 "Compose Up(전체)", 각 서비스 키 거터에서 "Up `mysql`"을 실행할 수 있다 |
| D4 | Compose run configuration | `Phantom Docker Compose` 타입. 설정 항목은 파일 목록, 프로젝트 이름, 서비스, 프로필, `--build`, 모드(`up -d --wait` 또는 attached)다 |
| D5 | Services 뷰 Docker 노드 | 맨 위에 "Docker (엔드포인트 이름)" 노드가 있고, 그 아래를 Compose 프로젝트, 서비스 컨테이너, 그 밖의 컨테이너, Testcontainers(접힘) 순으로 묶는다 |
| D6 | 컨테이너 동작 | Start, Stop, Restart, Remove, Logs(상세 패널에 따라가는 로그 콘솔), Inspect(JSON 읽기 전용 탭), Copy ID, 서비스에서 compose 파일의 해당 키로 이동 |
| D7 | 컨테이너 셸 | "Open Shell"을 누르면 Terminal 툴윈도에 `docker exec -it <id> sh`(가능하면 bash) 탭이 열린다 |
| D8 | 엔드포인트 탐지 | `DOCKER_HOST`, 그다음 현재 docker context, 그다음 기본 소켓 후보 순으로 찾는다. 설정 화면에서 직접 지정할 수도 있다 |

### 1.3 v0.2 이후

- **v0.2 Kubernetes 읽기 전용**
  - kubeconfig context 목록과 전환.
  - namespace별 Pod, Deployment, Service 목록과 Pod 로그를 `kubectl`로 가져온다.
  - 매니페스트 YAML을 JSON 스키마로 검증하고 완성한다(번들 스키마는 k8s 버전 하나).
- **v0.2 Docker 보강**
  - Compose 파일의 `${VAR}` 보간을 `.env`로 해석한다. community dotenv의 `environmentVariablesProvider`를 쓴다.
  - Dockerfile `FROM` stage 이름 완성.
  - `.dockerignore` 파일 타입.
  - 이미지 목록과 prune.
  - Compose 서비스 사이의 `depends_on` 참조 검증(존재하지 않는 서비스 이름).
- **v0.3**
  - `kubectl port-forward` 실행.
  - `kubectl apply --dry-run=server`와 diff.
  - Docker build run configuration.
  - Dockerfile 자체 lexer와 인스펙션(Ultimate 기능 이름 기준으로는 `DockerFileArgumentCount`, `DockerFileRunCommandMissingContinuation` 같은 종류).
  - Spring Boot `spring.docker.compose.file` 속성에서 compose 파일로 이동(Spring 설계 문서와 협의).

### 1.4 명시적 비목표

| 비목표 | 이유 |
|--------|------|
| 컨테이너 내부 파일시스템 접근(Eel/ijent, MRFS backend) | 측정된 Ultimate 비용의 주원인이다(§2). 사용자 워크플로에서도 필요하지 않다 |
| Dev Containers, Docker를 원격 인터프리터나 Run target으로 쓰기, 컨테이너 안 디버깅 | `clouds-docker-gateway`, `remoteRun` 영역이다. 클래스 수와 의존성이 크다 [M] |
| Docker over SSH, TCP+TLS 원격 데몬 | MVP는 로컬 unix socket만 지원한다. TCP는 v0.3 후보다 |
| 레지스트리 브라우징, push, 로그인 | 자격 증명을 다뤄야 한다. 필요하면 CLI를 쓴다 |
| Helm, Kustomize, Helmfile, Werf, Telepresence | 사용자가 쓰지 않는다. Ultimate K8s 76.5MB의 상당 부분을 차지한다 [M] |
| 클러스터 리소스 편집, 쓰기 API | v0.2는 읽기 전용이다 |
| Windows named pipe, Podman 전용 기능 | 대상 환경이 macOS다. Podman은 Docker 호환 소켓이 있으면 그대로 동작할 수 있다 [A] |
| 사용 통계(FUS) 수집 | 상주 비용만 들고 개인 빌드에는 쓸모가 없다 |

### 2.2 원칙

1. **사용할 때만 활성화한다.**
   - Docker 연결은 Services 툴윈도가 처음 보일 때 연다. 근거는 다음과 같다.
     - community `ServiceViewManagerImpl.loadGroups()`는 프로젝트를 열 때 contributor **인스턴스만** 만든다.
     - `getServices`는 `toolWindowShown`에서 처음 RESET 이벤트를 보낼 때 불린다 [V: `platform/execution.serviceView/src/ServiceViewManagerImpl.java` 884–925행].
     - 따라서 contributor 생성자는 비어 있어야 하고, 첫 `getServices` 호출 전에는 IO를 하지 않는다.
   - Compose 실행이나 컨테이너 동작을 하면 같은 연결을 쓴다.
   - K8s는 사용자가 "Kubernetes" 노드를 펼칠 때 kubeconfig를 읽는다.
2. **폴링하지 않고 증분으로 갱신한다.**
   - Docker는 `GET /events?filters={"type":["container"]}` 스트림 연결 하나로 변경을 받는다 [A: Docker Engine API].
   - 변경된 컨테이너만 `GET /containers/{id}/json`으로 다시 읽고 `SERVICE_CHANGED`/`SERVICE_ADDED`/`SERVICE_REMOVED` 이벤트를 보낸다.
   - 전체 RESET은 재연결할 때만 보낸다.
3. **프로젝트 전체를 무효화하지 않는다.**
   - Compose 파일 모델은 그 파일의 PSI에만 의존하는 `CachedValue`다.
   - `FileBasedIndex`를 새로 만들지 않는다. `PsiModificationTracker` 전역 카운터에 의존하지 않는다.
4. **서비스는 지연 생성하고 수명을 정리한다.**
   - 모든 상태는 `@Service`로 두고 생성자에서 `CoroutineScope`를 주입받는다.
   - 툴윈도가 10분 이상 숨겨져 있으면 이벤트 스트림을 닫는다. 다시 보이면 재연결과 RESET을 한다.
5. **EDT에서 IO를 하지 않는다.**
   - 소켓, 프로세스, 파일 읽기는 전부 `Dispatchers.IO`에서 한다.
   - EDT는 Services 뷰 모델이 이벤트를 반영할 때만 쓴다. 이 부분은 community 코드가 맡는다.
6. **비용을 측정해서 통과 여부를 정한다.** §4 각 단계의 acceptance에 "시작 JFR에서 `phantom.containers` 프레임 0개"를 넣는다.

## 3. 아키텍처

### 3.1 모듈 배치

```
plugins/phantom-containers/
├── plugin-content.yaml                       # jar ↔ content module 매핑 (plugins/yaml/plugin-content.yaml 형식 [V])
├── resources/META-INF/plugin.xml             # id: phantom.containers, content 선언만
├── core/            → content module  phantom.containers.core          (UI 없음)
│   └── src/.../engine/  DockerEndpointResolver, DockerEngineClient, UnixHttp, StreamDemux, model/*
├── compose/         → content module  phantom.containers.compose
│   └── deps: intellij.yaml, intellij.yaml.backend, intellij.json.backend
│   └── resources/schemas/compose-spec.json   # compose-spec 공식 스키마 (Apache-2.0) 번들
├── services/        → content module  phantom.containers.services
│   └── deps: intellij.platform.execution.serviceView, phantom.containers.core
├── terminal/        → content module  phantom.containers.terminal      (optional)
│   └── deps: intellij.terminal
├── dockerfile/      → content module  phantom.containers.dockerfile    (v0.1에서는 비어 있음, v0.3 lexer)
│   └── v0.1에서는 intellij.textmate 번들이 처리하므로 확장 없음
└── k8s/             → content module  phantom.containers.k8s           (v0.2)
    └── deps: intellij.yaml, intellij.json.backend, intellij.platform.execution.serviceView
        resources/schemas/k8s-1.30/*.json (core 그룹만 추린 standalone-strict)
```

- 각 하위 폴더에 `.iml`과 `BUILD.bazel`을 둔다.
  - community의 `BUILD.bazel`은 `.iml`에서 생성되는 "auto-generated section"을 쓴다 [V: `plugins/yaml/BUILD.bazel`]. 그래서 `.iml`을 먼저 쓰고 생성기를 돌린다 [A: 생성기 실행 방법은 확인 필요].
- 번들 등록은 `build/src/org/jetbrains/intellij/build/IdeaCommunityProperties.kt`의 `bundledPluginModules`와 `pluginLayouts`에 넣는다 [V: 61행, 67행]. 레이아웃 정의 예시는 `platform/build-scripts/src/org/jetbrains/intellij/build/CommunityRepositoryModules.kt`이고, textmate 번들 리소스 복사가 233행에 있다 [V].
- 기반 플러그인 `intellij.yaml`, `intellij.textmate.plugin`, `intellij.terminal`은 이미 `IDEA_BUNDLED_PLUGINS`에 들어 있다 [V: `platform/build-scripts/src/org/jetbrains/intellij/build/BaseIdeaProperties.kt`].
- community `plugins/env-files-support/docker/resources/intellij.dotenv.docker.xml`은 Ultimate 모듈 `intellij.clouds.docker.file`과 플러그인 `Docker`에 의존한다 [V]. phantom에서는 이 모듈이 로드되지 않는다. v0.2의 `.env` 연동은 우리 compose 모듈 안에 `ru.adelf.idea.dotenv.environmentVariablesProvider` 구현을 따로 둔다.

### 3.3 Docker Engine 클라이언트

- **전송**
  - JDK 16 이상의 `SocketChannel.open(StandardProtocolFamily.UNIX)`와 `UnixDomainSocketAddress`를 쓴다 [A: JBR 21에서 macOS 지원].
  - 그 위에 HTTP/1.1 클라이언트를 300줄 정도로 직접 쓴다. 요청 하나에 연결 하나를 열고 `Connection: close`로 닫는다. 이벤트와 로그 스트림만 오래 유지하는 연결이다.
  - `java.net.http.HttpClient`는 unix socket을 지원하지 않는다 [A]. ktor-client는 의존성 비용이 커서 쓰지 않는다.
- **API 버전 협상**
  - 먼저 `GET /_ping`을 보낸다. 응답 헤더 `API-Version`을 읽고, 최소 `v1.41` 이상이면 그 값을 경로 접두사로 쓴다 [A: Docker Engine API].
- **응답 처리**
  - `Transfer-Encoding: chunked`를 디코딩한다.
  - TTY가 없는 컨테이너 로그는 8바이트 헤더(stream type 1바이트, 0 3바이트, 길이 4바이트 BE)로 다중화돼 있으므로 `StreamDemux`로 stdout과 stderr를 나눈다 [A: Docker Engine API "Attach/Logs stream format"].
- **사용하는 엔드포인트** [A: Docker Engine API v1.41+]

| 동작 | 요청 |
|------|------|
| 목록 | `GET /containers/json?all=1` |
| 상세 | `GET /containers/{id}/json` |
| 시작/중지/재시작 | `POST /containers/{id}/start`, `/stop?t=10`, `/restart` |
| 삭제 | `DELETE /containers/{id}?force=0&v=0` (확인 다이얼로그 후) |
| 로그 | `GET /containers/{id}/logs?follow=1&stdout=1&stderr=1&tail=500&timestamps=0` |
| 이벤트 | `GET /events?filters={"type":["container"]}` |
| 버전 | `GET /version` (노드 툴팁에 표시) |

- **Compose 동작은 CLI로 한다.**
  - Engine API에는 compose 개념이 없다. 그래서 `docker compose -f <files> -p <project> [--profile p] up -d --wait [services]`, `stop`, `down`, `logs`는 `GeneralCommandLine`으로 실행한다.
  - 컨테이너가 어느 compose에 속하는지는 라벨로 알아낸다. `com.docker.compose.project`, `com.docker.compose.service`, `com.docker.compose.project.config_files`, `com.docker.compose.project.working_dir`를 쓴다 [A: compose v2 라벨].
- **엔드포인트 탐지 순서** (`DockerEndpointResolver`)
  1. 설정에서 직접 지정한 값.
  2. 환경 변수 `DOCKER_HOST`(`unix://`만 지원).
  3. `~/.docker/config.json`의 `currentContext` → `~/.docker/contexts/meta/<sha256(name)>/meta.json`의 `Endpoints.docker.Host` [A: docker context 저장 형식].
  4. 후보 경로 `/var/run/docker.sock`, `~/.docker/run/docker.sock`, `~/.colima/default/docker.sock`, `~/.orbstack/run/docker.sock`. 사용자 맥에서는 앞의 두 개가 있다 [V].
  - 탐지는 Services 노드를 처음 펼칠 때 한 번만 한다. 결과는 앱 서비스에 캐시한다.

### 3.6 스레딩

- **소켓 IO와 프로세스**
  - `DockerModelService`의 `cs`에서 `withContext(Dispatchers.IO)`로 돈다.
  - 이벤트 스트림은 코루틴 하나가 한 번에 한 줄씩 읽는다. 블로킹 read이므로 IO 디스패처 스레드 하나를 점유한다.
  - 취소되면 채널을 닫아 read를 깨운다.
- **Services 뷰**
  - `getServices`는 community가 백그라운드에서 부른다 [A: `ServiceModel` invoker 확인 필요].
  - 우리는 캐시된 스냅샷만 돌려주고, 연결이 없으면 "Connecting…" 노드 하나를 돌려준 뒤 연결을 시작한다.
- **동작**(Start/Stop 등)
  - `AnAction.actionPerformed`에서 `cs.launch`로 넘기고 진행 표시는 `withBackgroundProgress`로 한다.
  - `getActionUpdateThread()`는 `BGT`로 둔다.
- **PSI**
  - `RunLineMarkerContributor`와 스키마 판정은 하이라이팅 패스의 read action 안에서 돈다.
  - 파일 이름 검사 → 상위 키가 `services`인지 검사 순서로 끝내고 추가 조회는 하지 않는다.
- **Kotlin K2/UAST**
  - 이 플러그인은 Kotlin이나 Java 소스 PSI를 **건드리지 않는다**. 대상이 YAML, Dockerfile, 외부 프로세스뿐이다.
  - 따라서 K2와 UAST 지원 문제는 생기지 않는다.
  - v0.3에서 Kotlin 코드의 Testcontainers 선언과 연결하는 기능이 생기면 그때 UAST(`UastContextKt.toUElement`)로만 접근하고, K1 전용 API는 쓰지 않는다.

4. 터미널에서 `docker compose -f compose.yaml stop redis`를 실행한다. Services 아이콘이 1초 안에 바뀌어야 하고, 전체 트리가 깜빡이지 않아야 한다(증분 갱신 확인).
5. `./gradlew :adapter-module:test`처럼 Testcontainers를 쓰는 테스트를 돌린다. 컨테이너가 "Testcontainers" 그룹(접힘)에 들어가는지 확인한다.
6. `mysql-master`에서 Open Shell을 누르고 `mysql` 클라이언트에 접속한다.
7. Docker Desktop을 종료한다. Services 노드가 "Disconnected — Retry"로 바뀌는지, 로그에 예외 스택이 쌓이지 않는지 확인한다. 다시 시작한 뒤 Retry를 누르면 복구돼야 한다.
8. 유휴 30분 동안 JFR을 떠서 우리 패키지 CPU 샘플이 0인지 확인한다. 이벤트 스트림의 블로킹 read는 CPU를 쓰지 않는다.

## 6. 리스크와 남은 의문

### 6.1 리스크

| 리스크 | 영향 | 대응 |
|--------|------|------|
| Services 뷰 내부 API(`ServiceViewManagerImpl`, `@ApiStatus.Internal`)에 기대게 됨 | 업스트림 머지 때 깨질 수 있다 | 공개 인터페이스(`ServiceViewContributor`, `ServiceEventListener`)만 쓴다. 지연 로딩 동작은 테스트로 고정한다 |
| Docker Engine API 버전 차이, Docker Desktop과 colima의 소켓 차이 | 연결 실패 | `/_ping` 협상, 후보 경로 목록, 설정에서 직접 지정 |
| 수제 HTTP 클라이언트 버그(chunked 경계, keep-alive) | 목록이나 로그가 깨진다 | 요청마다 `Connection: close`. 녹화 응답 재생 테스트 |
| compose-spec 스키마가 Compose 최신 기능(`include`, `develop.watch`, `x-*`)보다 늦게 갱신됨 | 정상 키가 오류로 보인다 | 번들 스키마 버전을 기록한다. 원격 카탈로그 선호 옵션(`JsonSchemaCatalogProjectConfiguration.myIsPreferRemoteSchemas`) [V]을 문서로 안내한다. 인스펙션 수준은 WARNING으로 둔다 |
| SchemaStore 카탈로그가 같은 파일에 compose 스키마를 따로 붙여 스키마가 이중으로 매핑됨 | 경고가 중복된다 | community 기본값은 카탈로그 사용과 원격 활동이 켜짐(`myIsCatalogEnabled = true`, `myIsRemoteActivityEnabled = true`)이다 [V]. 우리 provider를 `SchemaType.embeddedSchema`로 등록해 카탈로그보다 우선하게 한다 [A: 우선순위 규칙 확인 필요] |
| Ultimate Docker 플러그인을 사용자가 따로 설치함 | 파일 타입과 Services 노드가 겹친다 | `plugin.xml`에 `<incompatible-with>Docker</incompatible-with>`를 선언한다 [A: 문법 확인] |
| `kubectl` 의존(v0.2) | kubectl이 없으면 동작하지 않는다 | 노드에 "kubectl not found, configure path"를 표시한다. exec 인증 플러그인(gke/aws/oidc)은 kubectl이 처리하므로 이 방식이 오히려 단순하다 |
| K8s 스키마 번들 크기 | 디스크가 늘어난다 | core 그룹 40여 kind만 추려 2–3MB 이하로 줄인다 [A] |
| Bazel `.iml` → `BUILD.bazel` 생성 절차를 모름 | 1단계가 지연된다 | 기존 플러그인(`plugins/yaml`)을 복제해 시작한다. 생성기 사용법은 `docs/` 또는 빌드 스크립트에서 확인한다 |

### 6.2 남은 의문

- [A] YAML 다중 문서(`---`)에서 JSON 스키마 검증이 문서마다 따로 적용되는가? K8s 매니페스트 한 파일에 여러 kind가 있을 때 필요하다. `plugins/yaml/backend/src/schema/` 쪽 walker를 확인해야 한다.
- [A] `ServiceViewContributor.getServices`가 백그라운드 스레드에서 불린다는 보장이 있는가? `ServiceModel`의 invoker 구현을 확인해야 한다.
- [A] `JsonSchemaFileProvider.isAvailable`이 호출되는 빈도. 파일을 열 때만 불리는지, 하이라이팅마다 불리는지에 따라 이름 판정 비용이 달라진다. 비용 자체는 정규식 한 번이라 작다.
- [A] TextMate `Dockerfile.*` 패턴이 `Dockerfile.md` 같은 파일까지 잡는가? 잡는다면 자체 `FileTypeBean.patterns`로 덮어야 한다.
- [U] Docker Desktop이 `/events` 스트림을 유휴 상태에서 끊는 주기. 재연결 정책(지수 백오프, 최대 30초)이 충분한지 측정해야 한다.
- [U] Spring Boot Docker Compose Support(`spring-boot-docker-compose`)가 앱을 시작할 때 compose를 올리면 run configuration이 올린 것과 같은 프로젝트 이름으로 묶이는가? 같은 디렉터리라면 기본 프로젝트 이름(디렉터리 이름)이 같아 같은 그룹에 들어갈 것으로 보인다.
- [U] Ultimate가 측정한 `eel.docker.mounts.aware.fs.enabled`의 의미 [M]. 우리는 MRFS를 아예 쓰지 않으므로 상관없다. 다만 다른 phantom 설계(원격 실행)가 MRFS backend를 추가한다면, 경로 접두사 트리 방식으로 바꾸자는 제안(`ult-other-plugins.md` §5의 1번)을 그 설계에서 다뤄야 한다.
